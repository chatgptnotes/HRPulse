## 1. Main Integration Goal

The long-term requirement is to exchange HR data between HRPulse and another Hospital Information Management System (HIMS), currently Adamrit. The integration must remain adaptable so another HIMS or other software can replace Adamrit later.

Required data exchange includes:

- Employee identity and master records.
- Employee attendance and presence records.
- Punch-in, punch-out, working hours, shift, late, absence, overtime, and missing-punch information.
- Salary inputs and final payroll results calculated according to HRPulse salary rules.
- Leave balances, leave history, leave applications, approvals, rejections, and approver notes.
- Employee documents, including resumes and educational qualification records.
- Payslips and salary history.
- HR notifications and announcements.

The intended ownership model is:

- Adamrit/HIMS authenticates its existing users.
- An employee is securely mapped to one HRPulse employee using an immutable identifier where possible.
- HRPulse remains the HR and payroll source of truth.
- Employees can access only their own HR information.
- Leave requests submitted in Adamrit are reviewed in HRPulse.
- HRPulse decisions and payroll results are synchronized back to Adamrit or another authorized client.
- All authorization must be enforced on the server, not only in the browser UI.

## 4. Security and Authentication Principles

The following constraints were established during the session:

- Authentication and authorization are different concerns.
- A successful login is not enough; the authenticated identity must have an HRPulse role or a secure employee mapping.
- All employee-scoped API requests must derive the employee identity from the authenticated server session or trusted integration token.
- The API must reject access to another employee's attendance, leave, payroll, document, or personal data.
- Production must not use a testing password embedded in frontend code, Markdown, source control, or deployment configuration.
- Service-role keys must remain backend-only.
- Browser applications must use only safe public configuration such as an allowed Supabase anonymous key.
- Integration endpoints should use short-lived tokens, signed requests, service credentials, or another server-to-server mechanism with auditing and replay protection.
- Document download endpoints require the same employee-level authorization as record endpoints.
- Logs should contain request identifiers and integration events without exposing passwords, tokens, salaries, or sensitive documents unnecessarily.

## 5. Authentication and Live-Site Troubleshooting Seen During the Session

Several authentication states were encountered:

### Authentication not configured

The HRPulse UI displayed:

```text
HRPulse authentication is not configured
```

This state means required frontend environment configuration was unavailable to the deployed frontend build, including values such as:

```text
VITE_SUPABASE_URL
VITE_SUPABASE_ANON_KEY
```

The backend also expected a configured bootstrap administrator email where applicable.

### Account has no HRPulse role

The login UI displayed:

```text
This account has no HRPulse role
```

This means authentication succeeded but HRPulse could not find an allowed role/mapping for the user. The fix belongs in backend authorization/bootstrap/profile mapping, not in a frontend-only bypass.

### HRPulse verification failure

The login UI also displayed an account verification retry state. This indicated the browser could authenticate but HRPulse role verification or the backend API was unreachable or returned an invalid result.

### Live-site page not found

The live login displayed:

```text
The page could not be found
```

This pointed to an incorrect or unavailable production API route/deployment mapping rather than an invalid password. Production frontend and backend route configuration must be checked together.

### Local versus production behavior

Local development and a pushed Git branch do not automatically update the production domain. The production deployment must:

- Build from the branch containing the desired commit.
- Receive the required environment variables.
- Deploy both frontend and backend/API routes correctly.
- Point the frontend to the correct live API base URL.
- Complete a new deployment after environment-variable changes.
